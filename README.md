# My Arena（自走棋）— 第一版

> **版本说明**：这是项目的第一版（1.0）。它的主要成果是把原型拆分成了 GUI、游戏逻辑和实体等目录，让整体结构比单文件实现稍微清晰；但这并不代表架构已经成熟。当前版本包含不少试错、临时实现和边界不清的问题，尤其是对象所有权、战斗状态与界面职责的划分。本文按现有代码说明项目，不把它包装成完成度很高的产品。

## 项目简介

这是一个使用 C++17 和 Qt Widgets 编写的桌面自走棋原型。程序提供准备、战斗和结算等阶段，包含棋盘与备战区、英雄商店、装备、玩家资源、羁绊/战斗逻辑，以及基于 Qt 数据流的存档读档入口。战斗包含移动、索敌和攻击的初步实现；现有实现更适合视为玩法与架构实验，而不是稳定、完整的自走棋规则系统。

## 技术与构建

- C++17
- Qt 6：Core、Widgets、Gui
- CMake 3.16 或更新版本

```bash
cmake -S . -B build
cmake --build build
```

### 主要类的职责（按当前实现）

- **`GameWindow`**：创建界面控件，处理鼠标拖放、双击购买、按钮操作和弹窗；通过 `GameManager` 读取或修改游戏状态，并响应其信号刷新 UI。
- **`GameManager`**：连接游戏阶段、玩家、棋盘、商店、装备和存档流程，是目前主要的协调/门面对象。它也承担了不少本应由更窄职责对象处理的规则。
- **`PreBoard`**：准备阶段棋盘和备战区的容器，分别以二维网格和一维备战区保存 `Unit*`。
- **`ComBoard`**：战斗阶段棋盘及行动循环。它读取单位行动意图，并执行移动等操作。
- **`Player`**：玩家的金币、生命、等级、上场人数、分数和刷新次数，并提供自身状态的序列化接口。
- **`Shop`**：商店格子容器。商店刷新、购买成本和与玩家资源的协调主要不在 `Shop` 内，而由上层逻辑/界面驱动。
- **`Unit` / 英雄子类**：保存英雄基础与战斗属性、装备/羁绊加成、行动状态，并实现战斗决策的基础接口；具体技能由英雄子类扩展。
- **`Equipment` / 装备子类**：保存装备名称、图片和属性加成。
- **`PieceWidget`、`EquipWidget`、`ParaWidget`**：将实体或玩家数据映射成 Qt 控件显示；它们是显示层控件，不是游戏数据模型。

## 当前阶段与已知问题

这部分是对第一版的刻意复盘。**结构稍微清晰，不等于职责边界清晰**；以下问题是现有代码的设计局限，不应被误解为已解决的功能。

### 1. 裸指针所有权混杂，存在生命周期风险

棋盘、商店和装备库都保存裸指针。`PreBoard` 析构时会删除棋盘和备战区中的单位，但商店、战斗棋盘也可能持有同一单位地址；`ComBoard` 从 `PreBoard` 取得的是指针引用，并没有复制单位对象。于是“谁拥有对象、何时销毁、某个指针是否只是借用”没有被统一表达。单位在棋盘与备战区移动时也依赖调用方先后执行放置和移除。

装备同样由裸指针在装备栏和单位之间转移。若转移过程失败、重复放置或对象同时被两个容器认为拥有，可能引发悬空指针、重复释放或泄漏。第一版目前靠调用顺序维持一致性，缺少类型层面的所有权约束。

### 2. 准备棋盘与战斗棋盘不是两个独立快照

`ComBoard` 初始化/重置时把 `PreBoard` 中的 `Unit*` 逐格拷入自己的网格，因此网格容器不同，但单位对象相同。战斗对单位 HP、CD、状态等字段的修改会影响同一对象；而 `ComBoard::clear()` 只清空战斗网格，不负责销毁棋子。这样的共享方式可能是原型阶段的简化，但“战斗副本”的命名容易让人误以为实体也被复制，准备阵容与战斗状态的隔离边界并不明确。

### 3. `GameManager` 与 GUI 都在做规则决策

`GameManager` 提供管理接口和流程控制，但 `GameWindow` 也直接判断准备/战斗阶段、检查金币和空位、扣钱、决定购买/升级/刷新能否执行，并直接对 `Unit` 调用穿脱装备、刷新属性等方法。规则被拆散在界面回调、管理器和模型中：同一规则难以集中测试，未来增加另一种 UI 或自动化测试也会遇到障碍。GUI 不只是呈现与转发输入，部分承担了应用服务和领域规则的工作。

### 4. `GameManager` 边界过宽

管理器同时负责阶段切换、计时器、战斗结算、敌方生成、棋盘操作、商店、玩家资源、羁绊应用及存档读档等协调。它是项目的中心入口，便于原型串接，但依赖面大、状态多，新增规则容易继续堆入同一个类。更清晰的边界可以是由应用层协调器编排独立的战斗、商店、存档服务及状态模型。

### 5. 容器接口与不变量保护较弱

`PreBoard` 对放置操作只检查目标是否为空，不验证传入指针、来源位置、单位是否已在另一格；移除操作直接置空，不负责返回或销毁对象。`Shop::placeUnitAt` / `removeUnitAt` 没有完整的下标保护。`ComBoard::getUnitAt` 和 `moveUnitFromTo` 也没有在自身接口中检查所有坐标与目标占用。由调用者维持所有前置条件，错误容易跨层传播。

### 6. 战斗行动使用字符串协议，算法与规则纠缠

`Action` 的移动和攻击类型用 `"Left"`、`"CommonAtt"` 等字符串表示，拼写错误只能在运行时暴露。`Unit::march` 同时负责索敌、选目标、CD 推进、决定攻击或移动并触发伤害；`ComBoard::marchEveryUnit` 又负责解释行动并更新网格，两者之间的边界较模糊。当前攻击分支在棋盘循环中主要改变状态，没有统一呈现完整的攻击结算流程；行动顺序也会受到逐格遍历和棋子移动的影响。战斗算法应视作早期尝试，尚不能代表完善的自走棋战斗模拟。

### 7. 属性与加成存在重复维护

`Unit` 同时保存基础属性、装备加成、羁绊加成和最终属性字段，并通过 `selfRefresh()` 由英雄类更新。装备对象和单位又分别记录装备加成；穿脱装备、羁绊变化和战斗中动态属性之间如何同步，依赖手动调用刷新。多个来源保存相似状态会带来遗漏更新或覆盖错误的风险。

### 8. 状态和存档协议仍偏脆弱

`Player` 将状态按固定字段顺序写入 `QDataStream`，从当前代码看没有明显的格式版本标识。随着字段变化，旧存档兼容需要额外处理。`GameWindow` 在选择文件后直接显示“成功”提示，界面也没有展示明确的保存/读取失败结果；存档交互与错误处理还较粗糙。项目目录里的 `.sav` 文件应视为本地样例，不能假设跨版本兼容。

### 9. 规则常量与随机行为缺乏集中配置

棋盘大小、商店槽位、金币花费、刷新次数、等级上限等数值散落在界面和逻辑代码中。随机数函数在每次调用时重新构造随机设备和引擎，使随机源难以注入、复现和测试。未来应使用统一配置及可注入的随机数生成器。

## 后续改进方向（不代表 1.0 已实现）

1. 先定义所有权：棋子和装备由单一所有者持有（例如 `std::unique_ptr`），其他系统仅持有明确的非拥有引用；或改用稳定 ID 与集中对象仓库，避免裸指针在容器间隐式转移。
2. 将购买、移动、升级、装备转移、刷新等操作封装成带校验的领域命令，由逻辑层原子地更新状态；GUI 只发送意图并显示结果。
3. 拆分过宽的 `GameManager`，明确阶段状态机、商店服务、战斗引擎、结算/奖励及存档序列化的边界。
4. 用枚举/结构化类型取代字符串行动协议；把“决策”和“执行”分离，并为战斗行动添加可重复的回合/时间步语义。
5. 明确准备阵容与战斗实体是共享对象还是独立快照，并据此设计战斗后状态同步，不依赖模糊的指针别名。
6. 集中配置规则常量；随机数引擎作为依赖传入，便于测试与复现。
7. 增加单元测试，优先覆盖棋盘边界、移动/购买失败回滚、所有权转移、战斗结算和存档读写；同时为存档增加格式版本和错误反馈。
